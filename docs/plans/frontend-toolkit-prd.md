## Problem Statement

hq's agent hub has domain toolkits for chatbots (`chatbot-toolkit`) and codebase
work (`codebase-toolkit`), but nothing for **frontend craft**. When an engineer
builds UI — components, state, styling, data fetching, forms, accessibility,
performance, or React Native screens — the org's agents fall back to generic
model knowledge with no house guidance, no checklists, and no version-grounded
snippets. There's no `frontend` routing signal in the taxonomy, so
`recommend-workflow` can't point a "build a UI" task at anything useful.

## Solution

Add a new optional plugin **`frontend-toolkit`**: a domain of **cross-cutting,
stack-agnostic frontend craft skills**. Twelve focused skills cover the
high-leverage web and mobile concerns. Each skill is a self-contained `SKILL.md`
plus a `references/` bundle (checklist, snippets, pitfalls), with every code
snippet grounded against current library docs via Context7 and pinned to explicit
version targets (React 19, current React Native/Expo).

The plugin wires into the hub the same way its siblings do: a `marketplace.json`
entry, taxonomy tags (`frontend`, `perf`), a regenerated catalog, a pointer from
the `feature-dev` playbook, and onboarding/README mentions. No new reference app
and no new workflow playbook — the skills are reached à la carte during the build
and review stages of an ordinary frontend feature.

Delivery is a **walking-skeleton PR** (plugin skeleton + vocab + one fully-wired
exemplar skill, `component-design`) to establish and CI-verify the pattern, then
**eleven dispatched workers** — one per remaining skill, one PR each.

## User Stories

1. As an hq engineer building a React UI, I want a `component-design` skill, so that I follow house guidance on composition, prop boundaries, and component shape instead of improvising.
2. As an engineer, I want a `state-management` skill, so that I choose correctly between local, server, and global state rather than reaching for one tool reflexively.
3. As an engineer, I want a `styling-systems` skill, so that I apply design tokens and a coherent styling architecture instead of ad-hoc CSS.
4. As an engineer, I want a `data-fetching` skill, so that I handle async loading, caching, and error/loading states the house way.
5. As an engineer, I want a `forms-and-validation` skill, so that I build accessible, well-validated forms without reinventing the wheel.
6. As an engineer, I want an `animation-and-motion` skill, so that I add motion that's performant and respects reduced-motion preferences.
7. As an engineer, I want an `accessibility-audit` skill with a WCAG checklist, so that I can audit and fix a11y issues against a concrete standard.
8. As an engineer, I want a `frontend-performance` skill, so that I diagnose and fix web-vitals/bundle/rendering problems with a repeatable method.
9. As an engineer, I want a `frontend-testing` skill, so that I test components and flows by behavior, not implementation detail.
10. As a mobile engineer, I want a `mobile-navigation` skill, so that I structure React Native navigation correctly from the start.
11. As a mobile engineer, I want a `touch-interaction` skill, so that I build gesture/touch UX that feels native.
12. As a mobile engineer, I want a `native-performance` skill, so that I keep React Native apps smooth (lists, bridge, render cost).
13. As an engineer with a vague UI task, I want `recommend-workflow` to route me to the frontend skills via a `frontend` tag, so that I discover the right skill without knowing its name.
14. As an engineer doing a frontend feature, I want the `feature-dev` playbook to point me at `frontend-toolkit`, so that the craft skills slot into the SDD build/review stages.
15. As an engineer reading any frontend skill, I want pinned version targets and Context7-grounded snippets, so that I trust the code is current and not a hallucinated API.
16. As an engineer, I want each skill to ship a checklist, a snippets file, and a pitfalls file, so that I get actionable artifacts, not just prose.
17. As a new hire running onboarding, I want `frontend-toolkit` listed among optional plugins, so that I can install it when I do UI work.
18. As a maintainer, I want every skill registered in `taxonomy.yml` with tags inside the locked vocab, so that hq CI stays green.
19. As a maintainer, I want the catalog regenerated by pre-commit/CI rather than hand-edited, so that it never drifts from the taxonomy.
20. As a reviewer, I want the exemplar skill merged first, so that the eleven dispatched skills have a proven pattern to copy.
21. As an org member, I want `frontend-toolkit` to be optional and self-contained, so that installing it never affects engineers who don't do frontend work.
22. As an engineer, I want skills framed stack-agnostically but exemplified in React/React Native, so that the guidance ports to Vue/Svelte while staying concrete.

## Implementation Decisions

**Framing**
- New **optional** plugin `plugins/frontend-toolkit/`, following the `<domain>-toolkit` naming convention.
- **Cross-cutting craft** skills, **no reference app**. Framing is stack-agnostic; concrete examples target React-family web + React Native mobile.

**Roster — exactly 12 skills**
- Web (9): `component-design`, `state-management`, `styling-systems`, `data-fetching`, `forms-and-validation`, `animation-and-motion`, `accessibility-audit`, `frontend-performance`, `frontend-testing`.
- Mobile (3): `mobile-navigation`, `touch-interaction`, `native-performance`.

**Skill shape (the reusable unit)**
- Each skill = `SKILL.md` + `references/checklist.md` + `references/snippets.md` + `references/pitfalls.md`.
- Every snippet authored by grounding against Context7 (`resolve-library-id` → `query-docs`) before writing the code block. Each skill states explicit version targets (React 19, current React Native/Expo).
- `component-design` is authored first as the **exemplar** that sets this shape; the other eleven replicate it.

**Taxonomy / routing (core-locked, core-group review)**
- Add `frontend` and `perf` to `taxonomy.yml` `vocab`.
- Register all 12 skills in the `skills:` map. Tagging: perf skills (`frontend-performance`, `native-performance`) → `[frontend, perf]`; `frontend-testing` → `[frontend, testing]`; `accessibility-audit` → `[frontend, review]`; the rest → `[frontend, feature-dev]`.
- `perf` is used only by the two perf skills initially; **no existing skills are retagged**.
- `catalog.json` is regenerated by pre-commit/CI — never hand-edited.

**Playbook**
- **No new workflow playbook.** Add a one-line pointer in `feature-dev.md`: building UI → reach for the `frontend-toolkit` skills during build/review.

**Manifests & docs**
- `marketplace.json` gains a `frontend-toolkit` entry; `plugin.json` author = HQ Core Team / raphaelsasso@ravn.co (matches siblings).
- `onboarding` optional-plugins step and `README.md` mention `frontend-toolkit` (mirrors the dispatch-kit precedent).
- `CHANGELOG.md` entry.

**Execution / slicing**
- **PR 1 — walking skeleton:** plugin skeleton + `marketplace.json` entry + vocab tags (`frontend`, `perf`) + `component-design` fully wired (skill + 3 references, taxonomy entry, regenerated catalog) + `feature-dev.md` pointer + README/onboarding/CHANGELOG. CI must be green.
- **Then dispatch ×11:** one autonomous worker (dispatch-kit) per remaining skill, each in its own worktree producing one PR. Each PR adds the skill dir + its taxonomy entry + regenerated catalog (CI requires a skill and its taxonomy entry land together).

## Testing Decisions

This is a markdown/skills plugin with **no runtime code to unit-test**. A good
"test" here is a static, behavioral gate on the artifacts — does the skill conform
to house structure and is its content trustworthy — not a check of authoring
internals.

- **hq CI gates** (existing, authoritative) verify every change: frontmatter validity, every `skills/*/SKILL.md` present in `taxonomy.yml`, all tags ⊆ `vocab`, catalog freshness, and no dangling refs. Each PR (skeleton and every dispatched skill) must pass these green before merge.
- **Code-review** (hq-core `code-review`) of each skill: prose quality, snippets traceable to Context7, version pins present, references actually actionable.
- **Prior art:** this mirrors how `chatbot-toolkit` and `codebase-toolkit` skills are verified — static CI + review, no bespoke test suite. The catalog-freshness and taxonomy-completeness checks are the existing prior-art gates the dispatched fan-out leans on.
- **No new test code** is added.

## Out of Scope

- A reference app (web or mobile) — skills are grounded via Context7, not extracted from running code.
- A dedicated `frontend-feature.md` workflow playbook — only a pointer in `feature-dev.md`.
- Snippet compile/type-check enforcement in a scratch project or CI toolchain.
- Retagging existing skills onto the new `perf` tag.
- Framework-neutral-only or mobile-only variants — the chosen scope is React-family web + React Native with portability notes.
- Any additional skills beyond the locked 12 (e.g. SSR/RSC deep-dive, i18n, design-system authoring) — deferred until a real need appears.

## Further Notes

- Sibling precedent for the mechanical wiring: commit `83f1a79` (dispatch-kit added to the onboarding optional-plugins step) and the `marketplace.json` / `taxonomy.yml` patterns already in the repo.
- The core-locked surface (vocab additions + `feature-dev.md` pointer + regenerated catalog) is concentrated in PR 1, so the eleven dispatched skill PRs are normal-review content changes that only touch `frontend-toolkit/` + their own taxonomy entry + catalog regen.
- Risk — **snippet drift:** Context7 grounding plus version pins mitigate hallucinated/outdated APIs, but CI cannot enforce snippet correctness; reviewers must spot-check. Called out so it isn't mistaken for a CI-guaranteed property.
- Risk — **catalog regen contention** across eleven parallel worker PRs: each regenerates `catalog.json`, so merges may need rebasing. Acceptable; the regen is deterministic from `taxonomy.yml`.
